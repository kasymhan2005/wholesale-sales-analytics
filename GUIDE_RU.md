# Как пользоваться проектом

## С чего начать

1. Распакуй архив целиком.
2. Открой `reports/dashboard.html` двойным щелчком. Для этого Python не нужен.
3. Прочитай `README.md`: это англоязычное описание для GitHub.
4. Открой `notebooks/sales_analysis.ipynb` в Jupyter: там код, пояснения и сохранённые результаты.
5. Для полного пересчёта установи зависимости и запусти команды из README.

В архиве уже есть данные, результаты и выполненный ноутбук. В репозиторий GitHub ничего автоматически не опубликовано.

## Что нужно понимать

**Почему нельзя считать строки заказами?** В одном заказе несколько товаров. 4603 строки — это 346 заказов. Количество заказов считаем через уникальный `order_id`.

**Почему `merge` проверяется?** Дубли в справочнике могут умножить строки и выручку. `validate='many_to_one'` проверяет, что справа одному ключу соответствует одна запись.

**Как считается выручка?** Количество × долларовая цена × курс на дату заказа. В итог входят только подтверждённые заказы. Это определение из курса, не прибыль.

**Что необычного произошло?** 13 марта было 19 отмен и 5 подтверждений. 14 марта 16 из 34 подтверждённых заказов совпадают с отменёнными по клиенту, менеджеру и товарам с их количествами. Поэтому часть скачка согласуется с повторным оформлением.

**Почему это не доказательство сбоя CRM?** У нас нет логов и причин отмен. Можно сформулировать гипотезу и предложить проверку, но нельзя утверждать причину как факт.

**Что добавлено сверх курса?** Проверки качества данных, точное сравнение корзин, защита от многократного сопоставления, ABC-анализ, концентрация выручки клиентов, тесты, повторяемый запуск и интерактивный HTML.

**Зачем ABC?** Показать, какая часть товаров формирует основную выручку. Это сегментация по выручке, а не по прибыли. Товары без продаж выделены отдельно.

**Почему нельзя сразу убрать товары без продаж?** Мы видим один месяц и не знаем наличие на складе. Нужен более длинный период и контекст.

## Как рассказать за минуту

Я работал с учебными данными оптовой компании из курса karpov.courses и расширил анализ для портфолио. С помощью Python объединил 382 CSV-файла, проверил качество данных и рассчитал показатели по 346 заказам. Отдельно исследовал всплеск заказов: нашёл 16 подтверждённых корзин, полностью совпадающих с отменёнными накануне. Добавил ABC-анализ, анализ клиентов и интерактивный дашборд. Основной вывод — рост числа заказов нужно проверять по статусам и составу корзин, потому что часть роста может быть повторным оформлением.

Используй этот рассказ после того, как самостоятельно разберёшь код и сможешь его запустить. При обсуждении процесса работы честно объясняй использование AI-помощи, если об этом спросят.

## Публикация
